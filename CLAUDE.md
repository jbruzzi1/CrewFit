# CrewFit / SpotMe — agent instructions

**Read `CLAUDE_HANDOFF.md` before doing any work.** It has the full context: stack, data model, correction history, and why each rule exists. `HANDOFF.md` is the engineer-facing technical summary.

This file is the short version — the rules that must never be missed.

## The hard rules

1. **NEVER deploy without Jeff's explicit "go."** Render the change, show him the image, wait. Never deploy-then-show. This is the one rule an agent already broke once (Aug 15, 2026) and it cost trust.
2. **You BUILD and you VERIFY. Jeff APPROVES. Then deploy.** Write the code, run the checks, render it, eyeball it, commit. Do not `fly deploy` on your own initiative.
3. **Show the FULL page in ONE image** — never isolated single-feature snippets. Jeff validates by eye on an iPhone 16 Pro, portrait (max-width 480px).
4. **Measure geometry** with `getBoundingClientRect` (x/y/w/h + baseline), not eyeballed widths. Paired buttons = equal size, same baseline.
5. **Bump the `?v=` cache-bust in `public/index.html`** on ANY frontend change. No build step exists — this is the only cache control.
6. **`npm test` before and after** anything touching progression, PRs, units or the log sheet — and add to it. Every assertion in `test/progression.mjs` exists because something was actually broken.
7. **Never add startup work to the top of `server.js`.** Use the *Boot migrations* block above `app.listen`. Three separate crashes have come from this; see §9 of `CLAUDE_HANDOFF.md`. The failures are conditional, so they do not show up in testing — one kilogram set in `data.json` was enough to stop the server booting for good.
8. **Before calling any change validated, ask: will this behave the same inside a native/wrapped app, not just the website version?** (Jeff, Sep 9, 2026, after the select-all-on-focus fix turned up a real iOS-Safari-only quirk with `.select()` on `<input type="number">`: "will this translate over when we are inside an app and not on a website version. I want us to ALWAYS remember and ask that question before we validate the change.") CrewFit is tested today as a website in mobile Safari (Playwright + Jeff's own iPhone). Anything that leans on browser-specific behavior — input selection/focus quirks, `history.pushState` (the sheet-dismiss-on-Back pattern), service workers/push, `localStorage`, viewport/keyboard handling, deep links — can behave differently once this ships inside an actual app wrapper.
   **Addition (Jeff, same day): "If browser specific - we avoid and FLAG TO JEFF. We want everything to translate over to an app."** This is not just a disclosure rule — prefer a non-browser-specific way to build the thing FIRST. Reach for a browser-specific API/behavior only when there's no reasonable alternative, and when you do, say so explicitly to Jeff before he approves it (what's browser-specific about it, and what happens to it in an app wrapper), rather than silently shipping it and only mentioning it if asked. Don't silently assume a website-only test covers the app case either way.
9. **Never lock in a subjective/creative call — wording, a label, a name, a color, copy, anything with more than one reasonable answer — by building it and showing Jeff the result.** Ask FIRST, before it's built. (Jeff, Sep 9 2026, after the PR/set-record feature shipped with a "WORK" badge label picked and built without asking him first, only explained after the fact alongside finished screenshots: "NEVER make changes like that without running them by me first. you never checked to confirm I like work.") Explaining the reasoning afterward, or inviting him to change it once it's already built, does not satisfy this — by then it is real code, a real screenshot, and a real thing he has to actively reject rather than an open question. The fix is the same shape as the copy-wordsmithing rounds earlier in this project (see CLAUDE_HANDOFF.md): surface 2-3 real options with the reasoning for each, or ask outright, and wait for Jeff's pick BEFORE writing it into the feature. This does not block objective, single-answer engineering work (a bug fix, a data-model change, wiring a test into `npm test`) — it's specifically for anything where a reasonable person could disagree with the choice made.
10. **Whenever making changes or additions, always run the proper math to make sure the visuals are centered/proper/the way they should be.** (Jeff, Sep 9 2026, standing rule — issued right after he spotted the PR/VOLUME pill text sitting visibly high in its pill from a zoomed screenshot, a real bug from `line-height:normal` reserving descender space that all-caps text never used.) This generalizes hard rule #4 and the "Double-check the visuals" bullet below from "do this for pills/segments/chips/buttons" to *every* visual change, without exception: before calling anything done, measure it — `Range.getBoundingClientRect()` of the actual text/glyph box against its container's `getBoundingClientRect()`, checking both vertical AND horizontal space on each side, not just one axis. Do not conclude something is centered from a screenshot by eye; screenshots are for catching what math alone would miss (actual color, real device rendering, layout in context), not a substitute for the measurement. If the math says it's off, it's off, even if it looks fine in a small preview.
    **This sandbox's own renderer is not a stand-in for Jeff's phone, and claiming otherwise is exactly the mistake to avoid** (same day, same rule: after round 1 of the pill-centering fix, a Chromium screenshot from THIS sandbox was shown as "looks properly centered to me now" — it wasn't, on Jeff's real iPhone, and it took him sending two more real photos before that got fixed for real. Jeff: "please write this to memory as you said it looked centered when it wasn't. We had to fix that.") The concrete gap: this sandbox only has Chromium, on Linux, without the fonts CrewFit's own CSS actually requests (`-apple-system` resolves to San Francisco on his iPhone; here it falls back to whatever generic sans-serif Linux has, a different font with different metrics) — and it has no WebKit engine at all (`playwright install webkit` is network-blocked here). For anything where font metrics/engine rendering could matter — vertical text centering being the clearest example, but the same caution applies to any pixel-tight visual claim — a measurement or screenshot taken in this sandbox is evidence about THIS sandbox's rendering, not proof about his device. State that limitation up front, the first time, not only after being corrected: say what render environment a screenshot came from, and if it's this sandbox's Chromium rather than his phone, say plainly that it's a reasonable check but not confirmation, and that his device is what actually decides it.
    **Reinforced Sep 20 2026 (Jeff, standing rule, after a new-button spacing round needed two follow-up corrections before it looked right): "RULE - Visuals matter. You've seen enough of how we do things and why we do things for visuals. When we create changes, new buttons, fields, etc - visual matters. We want the padding to not be too close to other areas. We want things to fit well. Think through with the proper math and not just 'here you go this works or solves the problem' fix."** Explicitly extends this rule to any NEW element (a button, a field, a control that didn't exist before) — not just adjusting something already on screen. Before showing Jeff a new element for the first time, measure its spacing to every neighbor it's new next to (gap above/below/beside, not just its own internal centering), the same `getBoundingClientRect()`-based way, and treat "it renders without errors" as unfinished, not done — the bar is "the spacing was actually reasoned about and measured," not "here you go, this works."
11. **Catch a bug — yours or pre-existing, critical or minor — and you MUST tell Jeff what it was and what you fixed or will fix, in the conversation, before moving on to anything else.** (Jeff, Oct 12 2026, after a scaling-fix session where a cold-review catch and a test-coverage gap were mentioned only in passing while work kept moving: "If you ever catch a bug - you MUST tell me what it was and what you fixed or will fix. You cannot just tell me you caught a serious bug and then move right on.") Saying "cold-review found a critical issue" or "caught a serious bug" and continuing on to the next step does not satisfy this, even if the real explanation eventually shows up later in a commit message or PR description — Jeff reads neither of those by default, and a detail that only exists there is a detail he was never actually told. The explanation (what broke, how it was found, what the fix was, how it was verified) belongs in the chat, in plain language, at the moment it's found — not deferred to a document he has to go dig up.
12. **Any time Jeff asks for a change or update, check it against whatever rearchitecture slice is currently in flight (see "Rearchitecture status" below) and flag it before starting, if it touches that slice's area.** (Jeff, Oct 12 2026, right after agreeing to the data-ownership rearchitecture and its slice-by-slice plan: "Please remind anytime I request a change or an update to something that may be having a migration going on.") The agreed shape of this (same conversation): only the ONE data domain actively mid-migration is off-limits to new work at any given time, not the whole app — and sessions/logs, when its turn comes, is the one slice big/central enough to warrant a longer heads-up. In practice: before starting any requested change while a slice is in flight, check "Rearchitecture status" below for what's currently being moved, and if the request touches that area, say so plainly and ask whether he wants to wait for that slice to finish, have it done against the new path directly, or proceed anyway knowing it adds risk — don't just silently proceed OR silently refuse. Keep "Rearchitecture status" itself up to date (which slice is active, which are done) every time a slice starts or finishes, so this check is actually answerable in a future session.
13. **Whenever you flag a risk, a potential bug, or a "this could go wrong" — in a pre-mortem or anywhere else — say right there whether the planned work already fixes it, unless it's obvious.** (Jeff, Oct 13 2026, after a pre-mortem flagged a race-condition risk and the fix for it was mentioned, but only in a separate paragraph further down, not attached to the risk itself: "when you write this, is this being fixed by this? Rule: when you write things like this always include after - 'This will be corrected with this fix' if it is not obvious.") Don't make Jeff connect a flagged risk to its fix himself by reading further down or into a different section — state it immediately after the risk, in the same breath: either "this gets fixed by [specific mechanism] as part of this work" or "this is NOT fixed by this change — it's a known, separate, still-open risk." Silence on this point reads as ambiguous, which is exactly what this rule exists to remove.

## Rearchitecture status (data-ownership migration)

Tracks the slice-by-slice move off "the whole DB lives as one JS object in one process's RAM" (see HANDOFF/this file's own history for the full reasoning — decided Oct 12 2026, Jeff: goal is App Store / real growth, so doing this now while stakes are low beats waiting for a tripwire). Planned order (least business-logic risk first, `sessions`/`logs` last on purpose): notifications/feed events → push subs/custom exercises/reports → crews → users → PRs (confirmed, no migration needed) → sessions & logs (confirmed complete Oct 18 2026 — decision #1 built/shipped, decision #2 confirmed no migration needed). **All planned slices are now done — hard rule #12's "don't touch the slice currently mid-migration" check has no active slice to flag against until a new one starts.**

- **Crews slice: COMPLETE and deployed as of Oct 16 2026.** Both decisions built, reviewed, fully tested, merged, and deployed: messages/challenges off the crew's blob onto their own tables (decision #1, PR #265), and the crew row itself (`name`/`ownerId`/`createdAt`/`memberIds`) normalized into real columns + a `crew_members` join table (decision #2). Next slice up: **users**. Full history:
  - **Two real, live-reproduced bugs found and fixed, same day, both inside `server.js`, no Postgres schema change involved:**
    1. **SEVERE — mutate-before-maybe-failing-save hazard in `DELETE /api/crews/:id/challenge/:challengeId`** (same bug class as the custom-exercise/report fix from the previous slice — see "Completed slices" below — just missed in crews at the time). The route removed the running challenge from `c.challenges` in memory BEFORE two awaited calls that can each fail (`pgDeleteFeedEvent`, then `save(DB)`). A rigged failure of either one correctly 500'd, but the challenge stayed gone from the live in-memory crew for the rest of the process's life (every other request reading that crew — `GET /api/crews/:id`, challenge-progress checks — saw it as already canceled), then silently REAPPEARED on the next restart, since the cancel was never actually persisted. **Reproduced live before fixing**: broke the `feed_events` table, canceled a running challenge, got a 500, then confirmed via a second `GET` that the challenge still showed as running — exactly the stranded state. Fixed by reverting (re-adding the challenge back to whatever `c.challenges` CURRENTLY is, not a blind restore of the pre-mutation array, so a concurrent legitimate change isn't clobbered) inside a `catch`, wrapped in the new `withCrewLock` helper below.
    2. **HIGH — real lost-update race on `PUT /api/crews/:id` membership edits.** The route reads `c.memberIds`, computes a new roster, assigns it, then runs real awaited Postgres calls (an `emitFeedEvent` per newly-added member, then `save(DB)`) before `res.json(publicCrew(c, ...))`. Because `c` is the same shared, mutable, process-wide object every request reads, a second genuinely-concurrent `PUT` on the SAME crew could run its own read-compute-assign in the window between the first request's assignment and its response — so the first request's own 200 body ended up echoing the SECOND request's roster, not the one it itself had just set. **Reproduced live before fixing**: two real concurrent `PUT`s, each adding a different member to an empty crew — one request's own response showed a roster it never asked for. Fixed with a new `withCrewLock(crewId, fn)` helper (mirrors db.js's own `enqueue()` pattern, keyed per crew id, auto-cleaned up once idle) that now wraps the ENTIRE route handler, cap-check through `res.json`, for both this route and the challenge-cancel route above — so two concurrent requests on the same crew can never interleave at all, each one's response is guaranteed to reflect exactly what it itself persisted. **Note what this does NOT claim**: `PUT /api/crews/:id` is a full-roster REPLACE, not an additive patch (see `validCrewMemberIds`) — two concurrent edits that each add a different member, based on a stale client-side snapshot of the roster, will still only end up with ONE addition surviving (whichever request's turn in the queue runs last fully overwrites the other). That's inherent to this endpoint's full-replace contract, not a concurrency bug, and a per-crew lock can't and shouldn't fix it — flagging it here as a known, accepted, NOT-fixed design limitation rather than letting it go undisclosed.

    - **Two independent review passes ran on this diff (safeguards step 4) and found FOUR real bugs, all fixed and verified same day:**
      1. **CRITICAL (adversarial review) — the boot migration could crash the whole server, permanently, on one malformed legacy row.** The first version handed every legacy array entry straight to `pgInsertCrewMessage`/`pgUpsertCrewChallenge` with no shape check; `crew_messages.id`/`crew_challenges.id` are `NOT NULL` primary keys, so a `null` entry or one missing `id` threw a raw Postgres constraint error straight through the boot IIFE's own `.catch(e => process.exit(1))` — exactly the "one bad row stops the server booting forever" failure mode hard rule #7 exists to prevent, reintroduced for crews. Fixed by skipping (not crashing on) any entry that isn't a real object with an `id`, same tolerance `scripts/migrate-to-postgres.mjs`'s own customExercises flatten already has. **Reproduced live and locked in**: a new regression block in `test/crew-messages-challenges-migration-differential.mjs` patches a crew with a mix of well-formed and malformed (null, missing-id, wrong-type) legacy entries and confirms the server boots, migrates only the well-formed ones, and stays healthy.
      2. **SEVERE (adversarial review) — message edit/delete weren't actually scoped to the crew in the URL.** `pgUpdateCrewMessageText`/`pgDeleteCrewMessage`'s SQL only matched on message id + the caller's own userId, never `crew_id` — the ROUTE checks membership against the crew in the URL, but the db.js call underneath never checked the message actually belonged to that crew. Since a message id is handed straight back to its author, this let someone edit/delete their own message through ANY crew they currently belong to, including one that has nothing to do with where the message actually lives (e.g. after being removed from the crew the message is really in, but still a member of some unrelated crew). Fixed by adding `crew_id` into both statements' `WHERE` clause, matching how `pgUpdateCrewChallengeFields`/`pgDeleteCrewChallenge` were scoped correctly from the start (the inconsistency between the two is what caught this). **Reproduced live and locked in**: a new block in `test/crews.mjs` posts a message in crew A, then confirms editing/deleting it via crew B's URL (a different crew the same user belongs to) 404s, while the real crew-A URL still works.
      3. **SEVERE (correctness/concurrency review) — challenge completion could double-fire under real concurrency.** `checkChallengeCompletion`'s "already completed?" check (`runningChallenge`, now async to reach Postgres) and its completed-at WRITE were two SEPARATE `enqueue()`'d Postgres calls — before this migration the whole check was synchronous, atomic for free; making it async to read Postgres reopened exactly the TOCTOU race `pgInsertCrewChallengeIfNoneRunning` was built to close for challenge-START, just never applied to challenge-COMPLETION. Two members finishing qualifying workouts within milliseconds of each other could both see "not yet completed" and both celebrate: two system messages, doubled notifications, two feed events. Fixed with a new `pgCompleteCrewChallengeIfNotAlready`, same one-atomic-statement shape as the challenge-start fix (`completedAt IS NULL` folded into the WHERE clause of the same UPDATE). **Reproduced live and locked in**: a new block in `test/crews.mjs` fires 10 genuinely concurrent completion attempts on the same challenge directly against db.js and confirms exactly one wins.
      4. **HIGH (correctness/concurrency review) — unguarded writes in that same function could 500 an otherwise-successful workout finish with its credit stranded.** `checkChallengeCompletion` is reached from `POST /api/sessions/:id/lock`/`.../leave` AFTER `creditFinish` has already mutated the session in memory; a thrown Postgres error inside it (unlike every other new write in this diff, which already catches-and-logs) would propagate past that point — the exact mutate-before-maybe-failing-write hazard this whole rearchitecture exists to eliminate, one level up the call stack. Fixed by wrapping the completion-and-celebration body in try/catch, logged not thrown, same best-effort treatment `emitFeedEvent` and the challenge-cancel feed cleanup already get.
      - **Also found by the adversarial review, considered and NOT a new bug:** restoring an old-style backup into a database with newer live crew_messages/crew_challenges data could, on the next boot's idempotent upsert, overwrite a since-edited message/challenge or resurrect a since-deleted one if the ids happen to collide. Judged inherent to restoring from any stale backup (the same is already true of every other field on a crew — a stale `memberIds`/`name` restores stale too), not something specific to or introduced by this migration, so left as an accepted property of disaster recovery rather than coded around.
      - A **MODERATE-HIGH finding from the adversarial review was also fixed**, found between the two review passes' initial reports and the fix: dropping `withCrewLock` entirely (not just its revert logic) from the message-post and challenge-start routes reopened a race against `DELETE /api/crews/:id`'s own lock-protected cleanup of `crew_messages`/`crew_challenges` — an insert that read the crew and passed its membership check could still land after the crew (and its cleanup) was already gone, orphaning a brand-new row nothing could ever reach or clean up again. Fixed by keeping `withCrewLock` on those two inserts — not for their own atomicity (the atomic Postgres functions already handle that), purely to serialize against concurrent deletion of the same crew.
    - **`DELETE /api/crews/:id` now also explicitly deletes orphaned `crew_messages`/`crew_challenges` rows** (`pgDeleteCrewMessagesByCrew`/`pgDeleteCrewChallengesByCrew`, best-effort, only after `save(DB)` has genuinely succeeded) — a cold-review catch made while building this, not from either review pass: deleting the crew used to throw away its messages/challenges for free (they lived inside the same blob); now that they're their own tables, nothing deletes them unless this does.

## Rearchitecture safeguards (per slice — mandatory, not optional)

(Jeff, Oct 13 2026, before any migration slice began: "I want you to employ safe guards... Have other agents critiquing and checking. With the logic, if I do this, what will break, what could go wrong, what bug may this make, what may be at stake.") This raises the bar above the standard "Verifying your own work" loop below for this specific project, because it's data-layer surgery on real user data, not a UI change. Every slice — no exceptions, including the "safe" early ones — goes through all of this, in order:

1. **Pre-mortem BEFORE writing any migration code for that slice.** In plain language, written out and shown to Jeff before building starts (not after): what could break, what data could be lost or corrupted, what concurrency risk this introduces (two requests racing against the new path, or one against old + one against new), what happens if the migration fails halfway through. This is the "if I do this, what will break, what could go wrong, what's at stake" Jeff asked for — it has to come first, not as a retroactive justification.
2. **Old and new paths run side by side during the transition** (dual-write + shadow-compare) — the new Postgres-backed path's output gets checked against the one actually driving real behavior before it's ever trusted alone.
3. **A ground-truth differential test** — same restart/full-rebuild-based proof technique used throughout this engagement (see `test/sessions-by-user-index.mjs`, `test/pr-rebuild-scoping.mjs` for the pattern) — proving the new path produces byte-identical results to the old one across realistic scenarios, not just the happy path.
4. **At least TWO independent review passes, each a fresh agent with no memory of how the code was built, each a different lens** — this is the "other agents critiquing and checking" (plural) Jeff asked for, not just one cold-review:
   - One reviewing for correctness/concurrency/data-loss risk (the standard cold-review this engagement already uses).
   - One actively, adversarially trying to break it — malformed input, races, partial failures, the migration itself getting interrupted mid-run.
5. **Any finding from either pass gets fixed and disclosed per hard rule #11** — never folded in quietly, never summarized as "found and fixed a bug" without the actual detail.
6. **When showing Jeff the finished slice:** state what the pre-mortem flagged, what each review pass checked and found (even "nothing" is worth saying explicitly), and name anything that could NOT be fully verified — never just "done."
